# Phase 4 Dependency / CVE Scanner

`DependencyScanner` consumes only Phase 1 admitted artifacts. It performs bounded static reads through `read_admitted_artifact`; no target package manager, build backend, `setup.py`, lifecycle hook, or target module runs. `scan_discovery` returns the existing `ScannerResult`; `scan_with_inventory` also exposes a normalized `DependencyInventory` and per-package `LookupResult` for a future orchestrator. The core scanner has no CLI or reporter. All network lookup is optional and disabled by `ScanSession.offline=True` (the default).

## Supported formats

| Ecosystem | Manifest | Lockfile | Notes |
| --- | --- | --- | --- |
| PyPI | `requirements.txt`, `requirements-*.txt`, `pyproject.toml` PEP 621 and narrow Poetry declarations, `Pipfile` | `uv.lock`, `poetry.lock`, `Pipfile.lock` | Requirements `-r` and `-c` read only already admitted root-contained files; `-c` is constraint metadata, never an installed package by itself. Markers are retained only by omission of environment evaluation, so applicability is uncertain. |
| npm | `package.json` dependency groups | `package-lock.json` v1/v2/v3 | v2/v3 `packages` entries and v1 nested dependencies are static; nested versions remain distinct. `yarn.lock` and `pnpm-lock.yaml` are unsupported and make coverage partial. |
| crates.io | `Cargo.toml` dependency, dev, build declarations | `Cargo.lock` | Only registry entries from crates.io are queryable. Git/path entries remain unresolved. |
| Go | `go.mod` `require` and `replace` | none | `go.sum` is a checksum list, not a resolved dependency graph, and is unsupported as a lockfile. Replacements are conservatively excluded from registry lookups. |

`.NET`, Java, Ruby, and PHP artifacts are recognized by discovery but are currently unsupported by the dependency parser and produce `DEPENDENCY_UNSUPPORTED_FORMAT` plus partial coverage. No resolver is invoked to fill gaps. For every format, malformed input yields a fixed diagnostic, and one bad artifact does not prevent other admitted artifacts from being parsed. Input is byte bounded before `json`/`tomllib` parsing; parser CPU and memory during a single call are not forcibly preempted.

## Inventory and precedence

Records carry canonical ecosystem, normalized package name, exact version or declared constraint, version kind (`exact`, `constraint`, `unresolved`, `vcs`, `local_path`, `url`), directness (`direct`, `transitive`, `unknown`), group, package source, root-relative source path, and optional logical lock path. PyPI names use PEP 503 style folding; npm scoped names are preserved; Go module paths remain case-sensitive. Invalid or unusually long coordinates are dropped. No fuzzy cross-ecosystem identity guess is made.

Within the same manifest directory, a lockfile exact version takes precedence over the declared manifest version while retaining declared constraint and source paths. Different resolved versions remain distinct instances and are queried separately. Repeated package/version records are queried once. Findings are deduplicated by ecosystem, normalized name, resolved version, and advisory ID; the first deterministic source location anchors the Finding. A manifest-only exact pin can be queried, but has MEDIUM confidence because the installed version is unverified. A resolved lock entry has HIGH confidence. Constraint-only, editable, local path, URL, and VCS records do not produce guessed CVE findings. Directness changes remediation wording, not advisory severity.

Hardening #5 adds a distinct `FIRST_PARTY_ROOT` identity for one narrow uv case. The scanner must have both an admitted scan-root `pyproject.toml` with a valid `[project].name` and an admitted scan-root `uv.lock` entry with the same normalized PyPI name and the sole source field `editable="."`. The exact `.` is lexical root metadata relative to that root lockfile; the scanner neither resolves nor follows any filesystem link. A missing manifest, same-name registry entry, conflicting same-name lock entries, nested lockfile, `../` editable path, or another local path fails this proof and remains governed by existing registry/local coverage rules. This is not workspace or monorepo resolution. The first-party root stays in `DependencyInventory` with both source paths, is never an OSV query key, and does not count as an unresolved third-party dependency or independently reduce completeness. Other local paths, VCS, URLs, and unresolved versions still make coverage partial. `ScannerSummary.details` and additive JSON 1.1 dependency fields expose `first_party_roots` and `unresolved_third_party`; `packages` still includes the root, while `exact_versions` counts queryable registry records.

## Provider and offline behavior

The `VulnerabilityProvider` protocol accepts exact `(ecosystem, name, version)` keys. `OSVProvider` uses the [OSV batch query](https://google.github.io/osv.dev/post-v1-querybatch/) for IDs, then the [OSV detail endpoint](https://google.github.io/osv.dev/get-v1-vulns/) for bounded normalized metadata. The endpoint is tool owned HTTPS, with no target-supplied URL, credentials, redirects, package manager, or subprocess. Queries are deduplicated, batched, count/byte/time bounded, and never retried aggressively (current retry count: zero). OSV batch pagination is treated as incomplete response and fails the batch closed; no partial-page result is presented as complete. The provider's exact-version response supplies affected status; this scanner does not implement ecosystem-specific range comparison. Only matching package detail fields are accepted. Withdrawn advisories are excluded from active results. Advisory IDs, CVE/GHSA aliases, fixed events, CVSS vector, safe reference URLs, timestamps, and a bounded summary are normalized; full OSV detail JSON is held only in bounded scan-local memory for ID reuse and never persisted or reported.

The cache stores normalized lookups, never target source, target paths, credentials, or raw provider payloads. Cache keys contain only provider schema plus ecosystem/name/exact version. Storage is JSON files under the user's tool-local cache directory (Windows `LOCALAPPDATA` when available), outside the selected target. Cache entries have schema and size checks and atomic replacement. Fresh entries are used in online or offline mode. Offline may use stale entries, sets `stale=true`, and marks scanner coverage partial. A cache miss offline yields `OFFLINE_NO_CACHE`, not `NO_MATCH`. Corrupt cache yields a diagnostic and no vulnerability assertion. Online stale entries are refreshed; provider failure becomes `QUERY_FAILED` and partial coverage. Cache files are local input and validated before findings.

## Live OSV validation (2026-09-24)

A gated integration test used only a synthetic `requirements.txt` containing the public exact pin `PyYAML==5.3.1`; it did not install or execute PyYAML. The formal `DependencyScanner` → `OSVProvider` → normalized lookup/Finding → target-external test cache → offline replay path succeeded under uv-managed Python 3.12.11. The successful flow sent one HTTPS `/v1/querybatch` request and two `/v1/vulns/{id}` detail requests, returning `GHSA-8q59-q68h-6hv4` and `PYSEC-2021-142`. Two `DEPENDENCY.KNOWN_VULNERABILITY` Findings were generated with manifest-pin MEDIUM confidence; advisory severity and bounded aliases, fixed versions, and references passed contract checks. These matches do not establish application reachability or exploitability.

The first live flow also obtained two normalized Findings but stopped on an incorrect test assertion about a domain field name; after correcting the test only, the same bounded flow was repeated successfully. Across both attempts there were two batch and four detail requests. The test cache was outside the synthetic target, contained normalized data without source paths or raw `affected` ranges, yielded one fresh offline cache hit, and was removed with the synthetic sandbox. Offline replay used a transport that would fail if invoked and recorded **zero** requests. No real target source, credentials, or machine path was sent. The live test runs only with `SECURITY_AUDITOR_LIVE_OSV_TEST=1`; default test discovery skips it and remains offline. Provider timeout and response limits remain 10 seconds and 1 MiB per response by default; TLS validation and the fixed HTTPS endpoint were not relaxed.

Live provider data and availability can change. Batch pagination still fails closed, timeout is best effort around a blocking request, and advisory metadata does not prove an application uses the affected function. Withdrawn, `NO_DATA`, and `NO_MATCH` distinctions remain covered by fake-provider/offline regressions rather than a second live scenario.

## Hardening #6: scan-global OSV request limits

The default online operation accepts at most 500 unique exact keys in batches of 50. Network calls are now limited across the **whole dependency scan** to 10 batch requests, 50 advisory detail requests, and 60 total requests (hard ceilings: 50, 500, and 550). The total counter equals batch plus detail calls. Each attempted transport call consumes one count; package-cache hits and scan-local advisory-ID reuse consume none. Existing 10-second request timeout, 1 MiB response cap, 16 MiB per-batch response cap, and best-effort 120-second total provider deadline remain unchanged. Target config cannot raise a hard ceiling.

The official OSV provider memoizes fetched detail by canonical advisory ID for one scan. The memo is not a persistent raw-response cache and is discarded afterward. Persistent cache entries remain normalized package/version lookups only. If a detail budget is reached mid-batch, already normalized active advisories still produce Findings; keys with unfetched IDs are explicitly incomplete, never cached as complete, and never converted to `NO_MATCH`. Remaining batches are not sent. Fixed diagnostics distinguish batch, detail, and total request limits; dependency coverage becomes `PARTIAL` and the default Gate blocks. JSON 1.1 adds optional provider request usage/limit counters, cache hits, dedup count, and a budget flag without changing existing `queries` (package-key) semantics. zh-TW HTML and console summarize usage and explain incomplete coverage.

The ten-coordinate pilot's mismatch was localized by a gated synthetic diagnosis: one valid HTTP 200 result held 106 advisory IDs above the local 100-ID limit. Hardening #7 keeps the limit but classifies valid overflow as incomplete coverage, rather than `BAD_RESPONSE`. The provider validates every ID in the byte-bounded list, stably deduplicates within each result, then selects the first 100 unique IDs per result subject to the existing 100-unique-ID per-batch cap. IDs beyond either cap are not detailed or treated as `NO_MATCH`. Aggregate `advisories_seen/accepted/truncated` counts refer to unique references per result, so repeated IDs across different package results can count in each result; detail requests still deduplicate by canonical ID across the scan. Malformed entries, including ones after the accepted prefix, remain `BAD_RESPONSE`.

An overflowed lookup is `incomplete`: confirmed matches remain Findings, while a lookup without a confirmed active match is `NO_DATA`, never `NO_MATCH`. The explicit `DEPENDENCY_OSV_ADVISORY_LIMIT_REACHED` diagnostic makes dependency coverage PARTIAL and Gate BLOCK. It can coexist with batch/detail/total request-budget diagnostics. A later detail timeout also preserves previously obtained findings while marking provider coverage incomplete; malformed detail still fails closed. Incomplete package/version lookups are not written to the complete-only persistent cache; scan-local advisory detail reuse remains bounded and is discarded after the operation. JSON 1.1 additively reports reference counts and the limit flag, while console and zh-TW HTML explain the safety truncation separately from confirmed Findings. See [RC validation](RC_REAL_WORLD_VALIDATION.md).

## Findings and interpretation

Rule `DEPENDENCY.KNOWN_VULNERABILITY` emits one normalized Finding per package/version/advisory. Evidence contains package coordinates, directness, provider, match status, stale flag, and bounded fixed versions. It contains no manifest section or full provider response. Severity is kept separate from confidence: a structured provider severity label is used when present; otherwise a conservative MEDIUM is marked `conservative_default`. A CVSS vector is preserved as text and no score is invented. An exact lock match is HIGH confidence; an exact manifest pin is MEDIUM. No generic CWE is guessed. Fixed versions are advisory metadata, not an automatic upgrade or a guarantee that one fix fits every branch.

**Known vulnerable dependency ≠ vulnerable function used ≠ attacker reachability ≠ exploitable application.** This phase makes no reachability or exploitability claim. It does not scan the installed runtime environment, infer typosquatting, perform license analysis, generate an SBOM, or modify the target. Findings from stale cache must remain labeled stale by future reporters.

## Completeness and limits

The default dependency budgets are 2 MiB/file, 32 MiB total, 20,000 entries/dependencies, include depth 8, and 300 seconds. The vulnerability budgets are 500 unique package versions, batches of 50, 100 advisory details per batch, **10 batch / 50 detail / 60 total network requests per scan**, 1 MiB/response, 16 MiB provider response per batch, 10 seconds/request, and 120 seconds across all provider batches (best effort around individual requests). Hard ceilings in `core/config.py` prevent unbounded operator config. Query and parse caps yield `aborted` or `partial` with fixed diagnostics; unsupported artifacts, unresolved versions, provider failures, stale/no cache, and incomplete discovery cannot appear as a clean completed vulnerability scan. `ScannerSummary.details` carries parser, inventory, cache, provider, and match counts. Online results depend on provider state; offline inventory and findings are deterministic for the same tree, cache, and config.

Remaining limits: local path checks are not a race-free Windows filesystem sandbox; `json`/`tomllib` CPU use is not preemptively isolated; PEP 508 and every ecosystem manifest dialect are not fully parsed; OSV coverage and advisory correctness are external; and network timeout is checked per request with a best-effort batch deadline. The full offline suite and one gated live OSV workflow passed under uv-managed Python 3.12.11. Real Windows junction and long-path checks passed separately; UNC remains unverified on this host.

# Phase 4 Dependency / CVE Scanner

`DependencyScanner` consumes only Phase 1 admitted artifacts. It performs bounded static reads through `read_admitted_artifact`; no target package manager, build backend, `setup.py`, lifecycle hook, or target module runs. `scan_discovery` returns the existing `ScannerResult`; `scan_with_inventory` also exposes a normalized `DependencyInventory` and per-package `LookupResult` for a future orchestrator. The core scanner has no CLI or reporter. All network lookup is optional and disabled by `ScanSession.offline=True` (the default).

## Supported formats

| Ecosystem | Manifest | Lockfile | Notes |
| --- | --- | --- | --- |
| PyPI | `requirements.txt`, `requirements-*.txt`, `pyproject.toml` PEP 621 and narrow Poetry declarations, `Pipfile` | `uv.lock`, `poetry.lock`, `Pipfile.lock` | Requirements `-r` and `-c` read only already admitted root-contained files; `-c` is constraint metadata, never an installed package by itself. Markers are retained only by omission of environment evaluation, so applicability is uncertain. |
| npm | `package.json` dependency groups | `package-lock.json` v1/v2/v3 | v2/v3 `packages` entries and v1 nested dependencies are static; nested versions remain distinct. `yarn.lock` and `pnpm-lock.yaml` are unsupported and make coverage partial. |
| crates.io | `Cargo.toml` dependency, dev, build declarations | `Cargo.lock` | Only registry entries from crates.io are queryable. Git/path entries remain unresolved. |
| Go | `go.mod` `require` and `replace` | none | `go.sum` is a checksum list, not a resolved dependency graph, and is unsupported as a lockfile. Replacements are conservatively excluded from registry lookups. |

`.NET`, Java, Ruby, and PHP artifacts are recognized by discovery but are currently unsupported by the dependency parser and produce `DEPENDENCY_UNSUPPORTED_FORMAT` plus partial coverage. No resolver is invoked to fill gaps. For every format, malformed input yields a fixed diagnostic, and one bad artifact does not prevent other admitted artifacts from being parsed. Input is byte bounded before `json`/`tomllib` parsing; parser CPU and memory during a single call are not forcibly preempted.

## Inventory and precedence

Records carry canonical ecosystem, normalized package name, exact version or declared constraint, version kind (`exact`, `constraint`, `unresolved`, `vcs`, `local_path`, `url`), directness (`direct`, `transitive`, `unknown`), group, package source, root-relative source path, and optional logical lock path. PyPI names use PEP 503 style folding; npm scoped names are preserved; Go module paths remain case-sensitive. Invalid or unusually long coordinates are dropped. No fuzzy cross-ecosystem identity guess is made.

Within the same manifest directory, a lockfile exact version takes precedence over the declared manifest version while retaining declared constraint and source paths. Different resolved versions remain distinct instances and are queried separately. Repeated package/version records are queried once. Findings are deduplicated by ecosystem, normalized name, resolved version, and advisory ID; the first deterministic source location anchors the Finding. A manifest-only exact pin can be queried, but has MEDIUM confidence because the installed version is unverified. A resolved lock entry has HIGH confidence. Constraint-only, editable, local path, URL, and VCS records do not produce guessed CVE findings. Directness changes remediation wording, not advisory severity.

## Provider and offline behavior

The `VulnerabilityProvider` protocol accepts exact `(ecosystem, name, version)` keys. `OSVProvider` uses the [OSV batch query](https://google.github.io/osv.dev/post-v1-querybatch/) for IDs, then the [OSV detail endpoint](https://google.github.io/osv.dev/get-v1-vulns/) for bounded normalized metadata. The endpoint is tool owned HTTPS, with no target-supplied URL, credentials, redirects, package manager, or subprocess. Queries are deduplicated, batched, count/byte/time bounded, and never retried aggressively (current retry count: zero). OSV batch pagination is treated as incomplete response and fails the batch closed; no partial-page result is presented as complete. The provider's exact-version response supplies affected status; this scanner does not implement ecosystem-specific range comparison. Only matching package detail fields are accepted. Withdrawn advisories are excluded from active results. Advisory IDs, CVE/GHSA aliases, fixed events, CVSS vector, safe reference URLs, timestamps, and a bounded summary are normalized; full OSV JSON is discarded.

The cache stores normalized lookups, never target source, target paths, credentials, or raw provider payloads. Cache keys contain only provider schema plus ecosystem/name/exact version. Storage is JSON files under the user's tool-local cache directory (Windows `LOCALAPPDATA` when available), outside the selected target. Cache entries have schema and size checks and atomic replacement. Fresh entries are used in online or offline mode. Offline may use stale entries, sets `stale=true`, and marks scanner coverage partial. A cache miss offline yields `OFFLINE_NO_CACHE`, not `NO_MATCH`. Corrupt cache yields a diagnostic and no vulnerability assertion. Online stale entries are refreshed; provider failure becomes `QUERY_FAILED` and partial coverage. Cache files are local input and validated before findings.

## Findings and interpretation

Rule `DEPENDENCY.KNOWN_VULNERABILITY` emits one normalized Finding per package/version/advisory. Evidence contains package coordinates, directness, provider, match status, stale flag, and bounded fixed versions. It contains no manifest section or full provider response. Severity is kept separate from confidence: a structured provider severity label is used when present; otherwise a conservative MEDIUM is marked `conservative_default`. A CVSS vector is preserved as text and no score is invented. An exact lock match is HIGH confidence; an exact manifest pin is MEDIUM. No generic CWE is guessed. Fixed versions are advisory metadata, not an automatic upgrade or a guarantee that one fix fits every branch.

**Known vulnerable dependency ≠ vulnerable function used ≠ attacker reachability ≠ exploitable application.** This phase makes no reachability or exploitability claim. It does not scan the installed runtime environment, infer typosquatting, perform license analysis, generate an SBOM, or modify the target. Findings from stale cache must remain labeled stale by future reporters.

## Completeness and limits

The default dependency budgets are 2 MiB/file, 32 MiB total, 20,000 entries/dependencies, include depth 8, and 300 seconds. The vulnerability budgets are 500 unique package versions, batches of 50, 100 advisory details per batch, 1 MiB/response, 16 MiB provider response per batch, 10 seconds/request, and 120 seconds across all provider batches (best effort around individual requests). Hard ceilings in `core/config.py` prevent unbounded operator config. Query and parse caps yield `aborted` or `partial` with fixed diagnostics; unsupported artifacts, unresolved versions, provider failures, stale/no cache, and incomplete discovery cannot appear as a clean completed vulnerability scan. `ScannerSummary.details` carries parser, inventory, cache, provider, and match counts. Online results depend on provider state; offline inventory and findings are deterministic for the same tree, cache, and config.

Remaining limits: local path checks are not a race-free Windows filesystem sandbox; `json`/`tomllib` CPU use is not preemptively isolated; PEP 508 and every ecosystem manifest dialect are not fully parsed; OSV coverage and advisory correctness are external; and network timeout is checked per request with a best-effort batch deadline. The full offline suite passed under uv-managed Python 3.12.11; real Windows junction/UNC/long-path behavior remains unverified on this host.
